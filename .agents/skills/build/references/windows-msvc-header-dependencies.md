# Windows MSVC header-dependency diagnostic

Read this only when a Windows/Ninja build fails to recompile after header changes, `ninja -t deps` reports `#deps 0`,
or stale objects are suspected.

## Verify the failure mode

On a non-UTF-8 Windows codepage, MSVC can emit a localized `/showIncludes` prefix whose bytes do not match the prefix
CMake cached during compiler identification. Ninja then records no header dependencies.

1. Run `ninja -C <BUILD_DIR> -t deps <object>` and check for `#deps 0`.
2. Inspect `msvc_deps_prefix` in `<BUILD_DIR>/CMakeFiles/rules.ninja` and the compiler-identification records in
   `<BUILD_DIR>/CMakeFiles/CMakeConfigureLog.yaml`.
3. Treat this diagnosis as confirmed only when the dependency record and cached prefix support it.

## Repair dependency discovery

Set `VSLANG=1033` for both configure and build. In VS Code CMake Tools, put it in `cmake.environment`, not only
`cmake.configureEnvironment`. Then use "CMake: Delete Cache and Reconfigure" or otherwise force compiler
identification to rerun. Confirm `msvc_deps_prefix = Note: including file: ` and that `ninja -t deps` lists headers.

`LANG`, `LANGUAGE`, `LC_ALL`, `chcp 65001`, or configure-only `VSLANG` do not by themselves correct a build-time prefix
mismatch.

## Recover stale objects safely

Do not start with `ninja -t clean <target>` on targets with protobuf/Mako outputs: it can remove generated byproducts and
force regeneration through an already dirty or uncompilable protocol tree.

Resolve and verify the absolute target path is inside `<BUILD_DIR>`, remove only affected `.obj`/`.pch` artifacts under
that target's `CMakeFiles/<target>.dir`, then rebuild. Use whole-tree object/PCH removal only when the diagnosis affects
the whole configured tree. Never remove source or generated protocol files as part of this recovery.
