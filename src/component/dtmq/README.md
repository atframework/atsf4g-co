## Writable 转移与订阅恢复

转移目标先初始化存储和角色，不生成新的创建日志。频道数据、创建或销毁状态由来源快照恢复，避免目标的新序号使来源快照被误判为旧数据。

转移快照携带存活订阅者的心跳时间、最后确认序号和哈希。日志、配置和订阅者均恢复后，新 publisher 按各订阅者的 checkpoint 立即补发；日志已压缩或 checkpoint 哈希不匹配时发送快照。随后广播只发送新日志，正常转移无需等待订阅心跳。

旧 writable 的转移 RPC 尚未结束时，收到的订阅心跳会更新本地进度，并在转发 TTL 允许时向实际转移目标尝试转发一次。转发失败不增加重试，由后续订阅心跳恢复。

日志压缩按序号立即删除边界之前的日志，保留边界日志，不依赖日志时间是否早于当前 tick。频道重建同样按新代际的创建序号清理，避免容量裁剪后误删新日志。

`auto_create=false` 允许已有可用的纯内存副本提升为 writable，但不创建或重建频道。忽略旧数据库记录时保留内存数据原有的待保存状态。

`custom_data_skip_notify` 仅跳过专用更新日志；noop 仍携带新的 custom-data 版本，保证副本和订阅者同步。客户端缓存分页遵守 `page_size`，缓存查询遵守 `max_count`（0 表示不限数量）。

## 回归测试

`test/` 覆盖真实转移 action 的数据恢复与即时补发、已有订阅者和重复转移、压缩或错误哈希的快照恢复、心跳转发成功与失败及 TTL 上限，以及服务端和客户端同 tick 压缩、满容量重建。

回归还覆盖数据更新和清空的推送分组、空更新无重复通知、旧数据库记录不能确认新数据已保存、非创建请求下的副本提升与销毁状态，以及客户端缓存分页边界。DTMQ fixture 显式使用空匹配参数合并规则表，其余资源沿用生成目录。

Team Room 的 WAL 集成用例验证转移后无需重新订阅即可应用事件，以及重建后的旧 checkpoint 通过快照恢复。

```powershell
ctest --test-dir build_jobs_cmake_tools -R 'dtmq|teamsvr-room' --output-on-failure
```
